結論：コードのバグである。func_get_kensu内のIF/ELSIF分岐にC_KBN_SHOKYAKU('03')用のELSIF節を追加し、償却資産テーブルに対する件数取得SQL生成関数（func_sql_cre_04_shokyaku相当）を新設・呼び出すことで修正する。

1. 直接原因（プログラム観点）

1-1. 該当ソースコード（実コード引用）

./src/01SQL/FUNCTION/PKG_ZEI_CERT_CALC.SQL

func_get_kensu関数（件数取得のディスパッチャ）は物件区分に応じて件数取得SQLを生成するが、IF分岐が土地('01')と家屋('02')にしか対応しておらず、償却資産('03')が渡されたときに何も実行されない。結果としてv_sqlがNULLのまま残り、件数0が返却される。

  FUNCTION func_get_kensu(i_year IN NUMBER, i_kbn IN VARCHAR2)
    RETURN PLS_INTEGER IS
    v_tbl   VARCHAR2(60);
    v_sql   VARCHAR2(4000);
    v_kensu PLS_INTEGER := 0;
    v_ret   PLS_INTEGER;
  BEGIN
    v_tbl := func_resolve_tbl(i_year, i_kbn);
    IF v_tbl IS NULL THEN
      p_log('W', 'func_get_kensu: unknown kbn=' || i_kbn);
      RETURN 0;
    END IF;

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    END IF;                                                -- ← C_KBN_SHOKYAKU('03')の分岐が存在しない
    -- ※ 上記以外（償却資産=03）のとき v_sql はNULLのまま

    IF v_sql IS NULL THEN
      -- 件数SQLが生成されなかった → 0件として返す           -- ← 償却資産は常にここに到達
      p_log('W', 'func_get_kensu: no count-sql for kbn=' || i_kbn);
      RETURN 0;
    END IF;

    EXECUTE IMMEDIATE v_sql INTO v_kensu;
    RETURN NVL(v_kensu, 0);
  EXCEPTION
    WHEN OTHERS THEN
      p_log('E', 'func_get_kensu: ' || SQLERRM || ' / kbn=' || i_kbn);
      RETURN 0;
  END func_get_kensu;
問題点：
  1. func_get_kensuのIF/ELSIF分岐にC_KBN_SHOKYAKU('03')のELSIF節が存在しないため、償却資産の件数取得SQL生成関数が呼び出されず、v_sqlがNULLのまま0件が返却される。
  2. そもそも償却資産用の件数取得SQL生成関数（func_sql_cre_02_tochi・func_sql_cre_03_kaokuに相当するもの）自体がパッケージ内に定義されていない。
  3. 件数が0のため、後続のfunc_calc_zeigakuが早期リターン(0円)し、さらにfunc_fmt_yenが0円を空文字列に変換するため、帳票上は課税標準額・税額ともに空白表示となる。

1-2. 処理フロー（任意：誤判定に至る流れ）

p_issue_certificate
(帳票種別='130'=償却資産証明書)→ p_get_target_kbn_list
(正しく'03'を返す)→ func_get_kensu(kbn='03')
IF分岐に'03'なし→v_sql=NULL→0件返却→ func_calc_zeigaku
(kensu=0→税額0円)→ func_fmt_yen(0)→空文字列
帳票に空白表示

2. 根本原因（設計・プロセス観点）

2-1. なぜ発生したか

  • リファクタリング時の移行漏れ：旧実装（帳票種別ごとにハードコード）から新ディスパッチ方式に移行した際、件数取得SQL生成関数の追加が土地・家屋のみに留まり、償却資産用の関数新設とディスパッチャへの登録が漏れた。ソース内コメントにも「当時から存在しなかった」と明記されており、旧来のバグが構造変更に引き継がれた形である。
  • 整合性チェック(p_self_check)の対象不備：保守用の整合性チェックプロシージャが土地・家屋のみを対象としており、償却資産の件数取得関数未定義を検知できなかった。
  • 帳票対象区分の設定と件数取得処理の不整合：p_get_target_kbn_listは帳票種別'130'に対し正しく'03'を返す設計だが、その下流のfunc_get_kensuが'03'を処理できない状態で放置されており、設計と実装間の矛盾が未検出のまま残存した。

2-2. なぜ事前に問題と判断されなかったか

テスト時に償却資産証明書の発行テストが実施されなかった、または土地・家屋の正常動作確認のみで合格とした可能性が高い。物件区分の全パターン（01/02/03）を帳票種別との組み合わせで網羅するテスト観点が欠落していた。また、件数0の場合にエラーではなく「ZERO_KENSU」ステータスで正常終了する設計のため、実行時例外が発生せず、ログ上もWARNINGレベルに留まり問題が顕在化しなかった。

2-3. 設計上の前提・業務仕様の誤認

観点本来あるべき仕様実装上の誤認
件数取得の区分対応帳票対象として定義された全物件区分（01/02/03）に対し、件数取得SQL生成関数が存在し、ディスパッチャから呼び出されること土地・家屋のみSQL生成関数を用意すれば十分であり、償却資産は対象外（または別系統で処理される）と誤認
件数0の扱い件数取得関数がSQL未生成でNULL返却する場合はエラー扱いとし、呼出元に通知すべき件数0は正常ケース（対象データなし）と同一視し、エラーハンドリング不要と判断

3. 修正案（変更前後）

修正方針は 「償却資産用の件数取得SQL生成関数を新設し、func_get_kensuのディスパッチャに償却資産('03')の分岐を追加する」こと。

3-1. 償却資産用 件数取得SQL生成関数の新設 および ディスパッチャへの分岐追加

(1) 変更前ロジック

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    END IF;
    -- ※ 上記以外（償却資産=03）のとき v_sql はNULLのまま

(2) 変更後ロジック

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_SHOKYAKU THEN                     -- ← 追加
      v_ret := func_sql_cre_04_shokyaku(v_tbl, v_sql);   -- ← 追加（新設関数呼出）
    END IF;

  --【新設関数】------------------------------------------------------------
  -- 件数取得SQL生成: 償却資産
  --   資産番号（SHISAN_NO）単位でCOUNT
  --------------------------------------------------------------------------
  FUNCTION func_sql_cre_04_shokyaku(i_tbl IN VARCHAR2, o_sql OUT VARCHAR2)
    RETURN PLS_INTEGER IS
    v_rtn PLS_INTEGER := 0;
  BEGIN
    o_sql := 'SELECT COUNT(*) FROM ' || i_tbl
          || ' WHERE BUKKEN_KBN = ''' || C_KBN_SHOKYAKU || '''';
    RETURN v_rtn;
  EXCEPTION WHEN OTHERS THEN
    v_rtn := -1;
    p_log('E', 'func_sql_cre_04_shokyaku: ' || SQLERRM);
    RETURN v_rtn;
  END func_sql_cre_04_shokyaku;
改善点
  • 償却資産('03')に対して件数取得SQLが正しく生成され、FIX_SHOKYAKU_yyyyテーブルから実件数が取得されるようになる。
  • 件数が正しく取得されることで、後続のfunc_calc_kazei_hyojun・func_calc_zeigakuも正常に動作し、課税標準額・税額が帳票に表示される。
  • 既存の土地・家屋の処理には一切影響を与えない（ELSIF追加のみ）。

※ 償却資産の件数カウント単位（資産番号単位／種類コード＋資産番号の複合キー等）は業務仕様・テーブル定義書と照合のうえ確定すること。上記例ではBUKKEN_KBN='03'の行数を単純カウントする最小限の実装としている。

4. 再発防止策

4-1. プログラム

No対策目的
P-1func_get_kensuのIF分岐末尾にELSE節を追加し、未知の物件区分が渡された場合はエラーステータスを返却する（silent failの排除）今後新たな物件区分が追加された際に対応漏れを即座に検知する
P-2p_self_checkに償却資産の件数取得関数チェックを追加する整合性チェックで対応漏れを自動検出可能とする
P-3p_get_target_kbn_listで返却される物件区分リストと、func_get_kensu内のディスパッチ対応区分の一致を起動時に検証するアサーション処理を追加する帳票対象定義と件数取得ロジックの不整合を構造的に防止する

4-2. テスト

  • 帳票種別×物件区分の全組み合わせ（110×01, 110×02, 120×01, 120×02, 130×03）で課税標準額・税額・件数が正しく算出されることを確認する結合テストケースを追加する。
  • 件数0となるケース（データなし）と件数SQLがNULL（ロジック未対応）のケースを区別するテストを追加し、後者がERRORステータスで検出されることを確認する。
  • 償却資産が存在する所有者に対して償却資産証明書を発行し、課税標準額≠0、税額≠0、件数≧1 であることを確認する正常系テストを必須ケースとして追加する。

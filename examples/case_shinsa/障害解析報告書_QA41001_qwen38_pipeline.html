事象
償却資産証明書を発行すると、課税標準額および税額が常に空白で表示され、件数欄も0件と表示される。データ上は当該所有者に償却資産が存在しており、0件になるのは不自然。
直接原因
件数取得ディスパッチャ func_get_kensu の IF/ELSIF に償却資産(C_KBN_SHOKYAKU='03')の分岐がなく、償却資産用の件数取得SQL生成関数自体が存在しないため、v_sql が NULL のまま NULL ガードで例外なしに常に0件を返す。この0件が func_calc_zeigaku で税額0を強制し、func_fmt_yen により 0/NULL が空欄になるため、件数0件・課税標準額空白・税額空白の3症状が出る。

2. 根本原因（設計・プロセス観点）

2-1. なぜ発生したか

  • 物件区分追加時の横断的整合の欠如: 償却資産(03)は定数(L13)・対象区分リストの130分岐(L271-274)・評価額SQL func_sql_hyoka(L117)・免税点 func_is_menzei(L202)・課税標準 func_calc_kazei_hyojun(L225)・明細行 func_build_meisai_line(L559)には追加されているが、件数取得ディスパッチャ func_get_kensu(L146-150)と償却用件数SQL生成関数のみ追加漏れ。区分を1つ追加する際に「触るべき箇所の一覧（チェックポイント）」が存在せず、局所的な追加に留まった。
  • 旧実装からの負債の引き継ぎ: コメントアウトされた旧ハードコード実装 func_kensu_hyoka_old(L605-618)でも「償却資産証明書(130)の分岐は当時から存在しなかった」(L614)。ディスパッチ方式へ移行した際に件数取得側の03未対応がそのまま継承された。
  • 失敗が例外化されない設計: 件数SQL未生成時に例外を投げず「0件として正常返却」する(L153-157)ため、障害が沈黙し発行自体は成功する（ZERO_KENSU は情報コードのみ）。

2-2. なぜ事前に問題と判断されなかったか

保守用整合性チェック p_self_check(L625-638) は func_sql_cre_02_tochi(土地) と func_sql_cre_03_kaoku(家屋) の2関数しか点検対象としておらず、償却資産の件数取得はチェック対象に含まれていない(L636)。かつ点検内容も「DUMMYテーブルでSQL文字列が生成されるか」のみで物理テーブル欠如を検知できない。加えてテストが土地・家屋中心で、償却資産証明書(130)の件数・課税標準額・税額を実データで検証する観点がなく、件数0でも異常終了せず正常発行されるため動作確認レベルで見逃されていた。

2-3. 設計上の前提・業務仕様の誤認

観点本来あるべき仕様実装上の誤認
償却資産証明書の集計対象償却資産証明書(130)は償却資産(03)の件数・評価額・課税標準額・税額をすべて算出し帳票へ出力する（パッケージ冒頭 L5-6 で対象帳票に明示）。件数取得だけ03未対応。件数0を「課税対象なし」と誤扱いし、func_calc_zeigaku で税額を強制0にして空白表示に連鎖させている。
件数0の扱いデータが存在するのに件数0になるのは異常であり、例外・エラーログ・発行停止などで検知すべき。件数0を正常系(o_status='ZERO_KENSU')として黙って通過させ、空白表示を正常結果とみなしている。
物件区分追加時の影響範囲区分追加は「対象区分リスト／件数SQL／評価額SQL／免税点／課税標準／自己点検」の全層に反映する。件数SQL層（生成関数+ディスパッチ）と自己点検層（p_self_check）への反映が漏れ、部分的な追加に留まった。

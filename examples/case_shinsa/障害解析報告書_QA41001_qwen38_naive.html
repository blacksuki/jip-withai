事象
償却資産証明書（区分130）を発行すると課税標準額・税額が常に空白、件数欄が0件となる。同一処理の評価証明書・公課証明書（土地・家屋）は正しく算出・表示される。データ上は当該所有者に償却資産が存在するため、0件になるのは不自然。
直接原因
件数取得ディスパッチ func_get_kensu（PKG_ZEI_CERT_CALC）に償却資産（03）の分岐がなく、常に0件を返す。件数0により func_calc_zeigaku が「課税対象なし」として税額0円を返し、func_fmt_yen が0を空欄表示するため税額（およびZERO_KENSU扱いの課税標準額）が空白になる。
根本原因
償却資産証明書対応時に、対象区分リスト・評価額取得・課税標準算出・免税点判定は03対応されたが、件数取得SQLの分岐のみ未追加（旧実装の130分岐欠落をディスパッチ方式へ移行する際に引き継いだ）。未対応区分が「Wログ＋0件返却」のサイレントフォールバックと、03を除外した自己点検 p_self_check の両方に見逃され続けた。
区分
プログラム不具合
結論：コードのバグ（プログラム不具合）。func_get_kensu に償却資産（03）の件数取得SQL分岐（新関数 func_sql_cre_04_shoyaku）を追加し、未対応区分のフォールバックを「サイレント0件」から明示エラーにすること。これにより件数・課税標準額・税額ともに正常に算出・表示される。データ・環境・仕様の問題ではない。

1. 直接原因（プログラム観点）

1-1. 該当ソースコード（実コード引用）

examples/case_shinsa/src/01SQL/FUNCTION/PKG_ZEI_CERT_CALC.SQL（パッケージボディ、func_get_kensu：L132〜、該当分岐 L144〜157）

償却資産証明書（帳票区分130）発行時、p_issue_certificate（L368）→ p_calc_shomeisho（L298）→ p_get_target_kbn_list（L257、130 は正しく ['03'（償却資産）を返す）→ func_calc_one（L283）→ func_get_kensu(年度, '03') の順で処理が進む。func_get_kensu 内の件数取得SQLディスパッチは土地（01）・家屋（02）の2区分のみの分岐であり、償却資産（03）はどの分岐にも当たらない。結果、アウト引数 v_sql が NULL のまま IF v_sql IS NULL に入ります。このとき例外を投げることも発行を止めることもなく、W（警告）ログを残すだけで「0件」として正常返却される。これが全件0件の直接原因である。

この「0件」が下流で税額を必ず0円にする。

最後に func_fmt_yen（L351）が 0（および NULL）を空文字 '' に変換するため、帳票上の税額欄は「常に空白」になる。件数欄は TO_CHAR(0) で「0件」と表示される。p_calc_shomeisho（L338〜340）は件数合計0に対し o_status := 'ZERO_KENSU' を立てており、パッケージ内コメントにも「件数0のときは課税標準額・税額とも空欄相当（0）となる」とある通り、0件化が帳票全体の空白表示に結びついている。

問題点：
  1. func_get_kensu（L144〜149）の件数取得ディスパッチに償却資産（03）の分岐がない。件数取得関数自体が存在しない（土地 func_sql_cre_02_tochi、家屋 func_sql_cre_03_kaoku のみ、03相当の関数なし）。償却資産証明書は常に0件になる。
  2. 未対応区分のフォールバックが「Wログ＋RETURN 0」のサイレント処理（L153〜157）。仕様上の欠落が「データなし」という正当な業務値に化け、発行は正常（o_result='ZERO_KENSU'）として完了してしまうため、本番で検知されなかった。
  3. func_calc_zeigaku（L243〜245）の「件数0＝課税対象なし＝0円」ゲートが、03 の件数0をそのまま「税額0円」に確定させる。データが存在しても税額は常に0円→空白表示になる。
  4. 本パッケージ内では評価額取得 func_sql_hyoka（L117）・課税標準算出 func_calc_kazei_hyojun（L225）・免税点判定 func_is_menzei（L202）はいずれも 03 対応済みで、件数取得だけが03未対応という非対称が存在する（後述2-1）。

1-2. 処理フロー（任意：誤判定に至る流れ）

償却資産証明書発行（帳票130）／対象区分 = 03→ func_get_kensu('03')：分岐なし → v_sql NULL → 0件（Wログのみ）→ func_calc_zeigaku：件数0 → 税額0円→ func_fmt_yen：0 → 空欄／件数「0件」／status=ZERO_KENSU
残りの確認事項（課税標準額の空白について）：パッケージ単体のトレースでは、課税標準額 func_calc_kazei_hyojun は件数に依存せず評価額から算出される（03分岐あり）ため、FIX_SHOKYAKU_年 テーブルに HYOKA_GAKU データがある限り非ゼロになる。本番で課税標準額も常に空白と観測されることは、①帳票表示層が ZERO_KENSU（件数0）時に課税標準額も空欄化する運用、または②償却資産テーブルの評価額カラム・値の問題のいずれかを疑わせる。修正適用後に課税標準額が復元されない場合は、表示層の空欄化ルールと FIX_SHOKYAKU_年 のカラム定義・実データ（03 の行に HYOKA_GAKU が格納されているか）を要確認とする。

2. 根本原因（設計・プロセス観点）

2-1. なぜ発生したか

  • 物件区分の分岐対応が各関数ごとに個別管理され、追加漏れが構造上起こり得た：「物件区分（01/02/03）ごとに IF/ELSIF を書いて分岐する」実装方式において、新区分（または新帳票）を追加する場合は対象区分リスト・件数取得・評価額取得・課税標準算出・免税点判定の複数箇所に同期して分岐追加が必要になる。今回のコードは評価額取得（func_sql_hyoka L117）、課税標準算出（func_calc_kazei_hyojun L225）、免税点判定（func_is_menzei L202）に 03 分岐が存在し、件数取得（func_get_kensu）だけが漏れている。区分リストと各計算関数は03対応済みなのに対して、件数SQL生成関数群（func_sql_cre_02_tochi／func_sql_cre_03_kaoku）に03相当がなく、func_get_kensu に ELSIF がない。同期追加のチェック工程が存在しないため、この非対称がそのまま本番入りした。
  • 旧実装の欠落が移行（リファクタ）で引き継がれた：ボディ末尾のコメント（L590付近）によると、旧実装は「帳票種別ごとに件数SQLをハードコード」しており、評価証明書（110）・公課証明書（120）のみで「償却資産証明書(130)の分岐は当時から存在しなかった」。ディスパッチ方式に移行した際に件数取得側のこの欠落がそのまま引き継がれている（コメント自体が「件数取得(func_get_kensu)側の区分対応漏れは引き継がれている」と認めている）。つまり、欠落は移行時の退行（リグレッション）ではなく、移行前から存在した欠落を移行後も誰も埋めなかったケースである。
  • サイレントフォールバックが欠落を業務値に偽装した：未対応区分を例外で止めるのではなく「Wログ＋0件返却」に設計されているため、件数0は「当該所有者に償却資産が無い」という正常なケースと区別不能になる。下流の税額計算も「件数0＝課税対象なし」を正当な前提としており、証明書は正常ステータス（ZERO_KENSU）で発行完結する。欠陥が「エラー」ではなく「正常な0」に見える設計だったため、運用上も検知されなかった。
  • 自己点検 p_self_check（L625）が03を除外していた：整合性チェックは土地・家屋の2関数のみを検査対象とし、「※ 償却資産の件数取得関数はチェック対象に含まれていない」「本来はここで償却資産の未対応を検知できるはずだが」とコメントが認めている通り、検出できる仕組みが意図的に（または偶然に）03を除外していた。

2-2. なぜ事前に問題と判断されなかったか

① テスト対象帳票が評価証明書・公課証明書（土地・家屋）に偏っており、「償却資産証明書（130）＋データ有」のケースが存在しなかった。130を発行しても、その環境に償却資産データが無い所有者では「0件・空白」が仕様通りと見分けがつかないため、欠落が発見されなかった。② p_self_check が03を除外しているため、リリース時点の整合性チェックでも検出できなかった（110/120の分岐健全性しか確認されない）。③ 発行結果ステータス（ZERO_KENSU）の発生傾向を監視する運用が無く、03証明書で常に ZERO_KENSU が立つ異常も可視化されなかった。④ 件数0→税額0は下流の正当な設計（課税対象なし）と一致するため、個々の関数は単体で見ると「正しく」動作しており、結合して初めて顕在化するバグであった。

2-3. 設計上の前提・業務仕様の誤認

観点本来あるべき仕様実装上の誤認
件数取得のカバレッジ証明書で対象となり得る全物件区分（01土地／02家屋／03償却資産）について件数取得SQLが定義され、ディスパッチで網羅される01・02のみ定義・分岐。03は件数取得関数自体が存在せず NULL→0件。対象区分リスト（130→03）と件数取得の対応表が非同期で管理されていた
未対応区分の扱い仕様上あり得ない区分・未実装区分は明示エラー（またはNGコード）として発行を止め、原因を露出させるWログを残すだけで0件を正常返却。「0件＝データなし」という業務値に欠落が偽装され、下流がそのまま正当な0として処理
整合性セルフチェック対象区分リストに含まれる全物件区分の件数取得SQL生成を検査する検査対象が土地・家屋にハードコード。償却資産（03）の未対応を検知できない構造
空欄表示の意味「データなしによる0」は表示上も検知・区別可能（ステータス表示や監査ログで確認できる）func_fmt_yen が0を空欄表示（「現状は空欄運用」）するため、帳票上はエラーと正規の0を区別できず、現場は「空白＝不自然」にしか見えない状態

4. 再発防止策

4-1. プログラム

No対策目的
P-1「件数SQLが生成されなかった（v_sql IS NULL）」経路を RETURN 0 から RAISE_APPLICATION_ERROR（またはNGコード返却）へ変更し、発行結果が ERROR となるようにする（3-2実施）未対応・不備を「正当な0件」という業務値に偽装させず、常に露出させる
P-2物件区分別の「件数取得SQL生成が定義されているか」の検査を p_self_check が p_get_target_kbn_list の対象区分を走査する形に拡張し、リリースゲートで必須化（3-2実施）区分追加時の分岐漏れをセルフチェックが自動検出する（ハードコードされた検査対象リストの非同期化を防ぐ）
P-3物件区分・帳票種別を追加する開発チェックリストに「kbn 分岐を持つ全関数（件数取得／評価額取得／課税標準算出／免税点判定／セルフチェック）に新分岐が揃っているか」の突合項目を追加設計・開発段階で「区分リストと計算関数の非対称」を作らせない

1. 直接原因（プログラム観点）

1-1. 該当ソースコード（実コード引用）

case_shinsa/src/01SQL/FUNCTION/PKG_ZEI_CERT_CALC.SQL

func_get_kensu の物件区分ディスパッチIF文に C_KBN_SHOKYAKU('03') の分岐が存在せず、償却資産の場合 v_sql が NULL のまま残り、常に件数 0 が返される。

問題点：
  1. func_get_kensu 内の IF/ELSIF に C_KBN_SHOKYAKU('03') 用の分岐がなく、件数取得SQL生成関数(func_sql_cre_XX_shokyaku 相当)も未実装
  2. v_sql が NULL のとき例外ではなく 0 を静かに返すため、呼出側は正常系と区別できない

2. 根本原因（設計・プロセス観点）

2-1. なぜ発生したか

  • 旧実装(func_kensu_hyoka_old)が土地・家屋のみ対応で償却資産の件数取得ロジックが元々存在しなかった。ディスパッチ方式へのリファクタリング時にも、件数取得関数(func_sql_cre_XX)を償却資産用に新設する作業が漏れた
  • 評価額取得(func_sql_hyoka)や課税標準額計算(func_calc_kazei_hyojun)は3区分すべてに対応済みだが、件数取得のみ2区分で止まっているという非対称な実装状態に気づかれなかった

2-2. なぜ事前に問題と判断されなかったか

保守用の p_self_check が土地・家屋の件数取得関数しか点検対象にしておらず、償却資産の件数取得未対応を検知できなかった。コード内コメントにも「チェック対象に含まれていない」と明記されているが放置されている

2-3. 設計上の前提・業務仕様の誤認

観点本来あるべき仕様実装上の誤認
件数取得ディスパッチャで全物件区分をカバーすべき01=土地, 02=家屋, 03=償却資産 の3区分すべてに件数取得SQL生成関数を実装し、func_get_kensu のIF分岐に含める土地・家屋の2区分のみ対応すれば十分と誤認（旧実装の制約をそのまま踏襲）

3. 修正案（変更前後）

修正方針は 「func_get_kensu の物件区分ディスパッチIF文に償却資産(C_KBN_SHOKYAKU='03')用の分岐および件数取得SQL生成関数を追加し、p_self_check にも償却資産の点検を加える。」。

4-1. プログラム

4-2. テスト

  • 償却資産証明書(130)を指定して p_calc_shomeisho を実行し、FIX_SHOKYAKU_YYYY テーブルにデータがある場合に o_kensu_total > 0, o_kazei_total > 0, o_zei_total > 0 が返ることを確認

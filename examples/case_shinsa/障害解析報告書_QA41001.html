事象
償却資産証明書を発行すると課税標準額・税額が常に空白、件数も0件と表示される。同一処理でも評価証明書・公課証明書（土地・家屋）は正しく算出される。
直接原因
件数取得ディスパッチャ func_get_kensu に償却資産(03)の分岐が無く、件数SQLが未生成のまま常に0件を返すため。
根本原因
物件区分の追加が「対象区分リスト決定」には反映されたが「件数取得」以降の分岐に反映されず、区分追加時の横断的整合が担保されていない。
区分
プログラム不具合
結論：コードのバグである。現場コメント「そもそも集計処理に入っていない」は半分正しく半分誤りで、対象区分リスト（p_get_target_kbn_list）には償却資産(03)が正しく含まれており集計ループには入っている。しかしループ内で呼ぶfunc_get_kensuが償却資産の件数SQLを生成しないため件数=0となり、その0がfunc_calc_zeigakuおよびfunc_fmt_yenを通じて税額0→空白表示へ連鎖する。修正はfunc_get_kensuに償却資産(03)の件数取得分岐を追加すること。

1. 直接原因（プログラム観点）

1-1. 該当ソースコード（実コード引用）

src/01SQL/FUNCTION/PKG_ZEI_CERT_CALC.SQL

件数取得のディスパッチャ func_get_kensu は、物件区分ごとに件数取得SQLを選択する。しかし分岐が「土地(01)」「家屋(02)」の2つしか無く、「償却資産(03)」の分岐が欠落している。このため償却資産では v_sql がNULLのままとなり、直後のNULLガードで 0件 を返して処理が抜ける。

  FUNCTION func_get_kensu(i_year IN NUMBER, i_kbn IN VARCHAR2)
    RETURN PLS_INTEGER IS
    v_tbl   VARCHAR2(60);
    v_sql   VARCHAR2(4000);
    v_kensu PLS_INTEGER := 0;
    v_ret   PLS_INTEGER;
  BEGIN
    v_tbl := func_resolve_tbl(i_year, i_kbn);
    IF v_tbl IS NULL THEN
      p_log('W', 'func_get_kensu: unknown kbn=' || i_kbn);
      RETURN 0;
    END IF;

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    END IF;
    -- ※ 上記以外（償却資産=03）のとき v_sql はNULLのまま   -- ← ここが欠落。03の分岐が無い

    IF v_sql IS NULL THEN
      -- 件数SQLが生成されなかった → 0件として返す
      p_log('W', 'func_get_kensu: no count-sql for kbn=' || i_kbn);
      RETURN 0;                                              -- ← 償却資産は常にここで0件RETURN
    END IF;

    EXECUTE IMMEDIATE v_sql INTO v_kensu;
    RETURN NVL(v_kensu, 0);
  EXCEPTION
    WHEN OTHERS THEN
      p_log('E', 'func_get_kensu: ' || SQLERRM || ' / kbn=' || i_kbn);
      RETURN 0;
  END func_get_kensu;

0件が返った後の連鎖箇所（税額算出・金額整形）は以下のとおり。件数0を受けて税額0、金額0を受けて空文字が返るため、最終的に課税標準額・税額とも空白表示となる。

  -- 税額の算出（i_kensu=0 で必ず0円）
  FUNCTION func_calc_zeigaku(i_kbn IN VARCHAR2, i_kazei_hyo IN NUMBER, i_kensu IN PLS_INTEGER)
    RETURN NUMBER IS
    v_zei NUMBER := 0;
  BEGIN
    IF NVL(i_kensu,0) = 0 THEN
      RETURN 0;              -- ← 償却は件数0のため税額も強制的に0
    END IF;
    ...
  END func_calc_zeigaku;

  -- 金額→文字列（0円は空欄運用）
  FUNCTION func_fmt_yen(i_val IN NUMBER)
    RETURN VARCHAR2 IS
  BEGIN
    IF i_val IS NULL THEN
      RETURN '';
    END IF;
    IF i_val = 0 THEN
      RETURN '';              -- ← 0円は空白表示。課税標準0/税額0が空白になる
    END IF;
    RETURN TO_CHAR(i_val, 'FM999,999,999,990') || '円';
  END func_fmt_yen;
問題点：
  1. func_get_kensu のディスパッチ分岐に償却資産(C_KBN_SHOKYAKU='03')が無く、件数SQLが生成されない。func_sql_hyoka は03に対応済みで評価額は取得できるのに、件数だけが常に0となる非対称な実装。
  2. 件数0が func_calc_zeigaku（NVL(i_kensu,0)=0→0）と func_fmt_yen（0→''）を通じ、件数0件・課税標準額空白・税額空白の3つの症状に連鎖する。土地・家屋は件数SQLが存在するため正常に算出され、事象説明と完全に一致する。

1-2. 処理フロー（誤判定に至る流れ）

償却資産証明書(130)発行→ p_get_target_kbn_list
→ 03を正しく返す→ func_calc_one → func_get_kensu(03)→ 03の件数SQL分岐が無い
v_sql=NULL → 0件RETURN→ 税額0(func_calc_zeigaku)
→ 空白(func_fmt_yen)

※ 現場コメント「集計処理に入っていない」の検証：対象区分リスト決定 p_get_target_kbn_list は償却資産証明書(130)に対し償却資産(03)を正しく返しており、集計ループ（p_calc_shomeisho / p_build_meisai_body）には入っている。入っていないのは「件数SQLの生成」だけであり、原因はロジックの物件区分考慮漏れと確定できる。

2. 根本原因（設計・プロセス観点）

2-1. なぜ発生したか

  • 区分追加時の横断的整合の欠如：償却資産(03)は定数(C_KBN_SHOKYAKU)・対象区分リスト・評価額SQL(func_sql_hyoka)・免税点判定・課税標準算出には追加されているが、件数取得ディスパッチャ func_get_kensu だけに追加漏れがある。物件区分を1つ追加する際に「触るべき箇所の一覧」が存在せず、局所的な追加に留まった。
  • 旧実装からの負債の引き継ぎ：コメント（廃止済み func_kensu_hyoka_old）にあるとおり、旧ハードコード方式でも償却資産(130)の分岐は元々存在しなかった。ディスパッチ方式へ移行した際に件数取得側の03未対応がそのまま引き継がれた。
  • 失敗が例外化されない設計：件数SQL未生成時に例外を出さず「0件として正常返却」しているため、障害が沈黙し発行自体は成功してしまう（o_status='ZERO_KENSU'）。

2-2. なぜ事前に問題と判断されなかったか

保守用の整合性チェック p_self_check は「土地・家屋」の件数取得関数しか点検対象にしておらず、償却資産の未対応を検知できない（コメントにも「償却資産の件数取得関数はチェック対象に含まれていない」と明記）。加えてテストが土地・家屋中心で、償却資産証明書の課税標準額・税額・件数を実データで検証する観点が漏れていた。件数0でも異常終了せず正常発行されるため、動作確認レベルでは見逃されやすい。

2-3. 設計上の前提・業務仕様の誤認

観点本来あるべき仕様実装上の誤認
償却資産証明書の集計対象償却資産(03)の件数・評価額・課税標準額・税額をすべて算出して帳票へ出力する件数取得だけ03未対応。件数0を「課税対象なし」と誤って扱い、税額・課税標準額も0＝空白に連鎖
件数0の扱いデータが存在するのに件数0となるのは異常。検知・是正が必要件数0を正常系（ZERO_KENSU）として黙って通過させ、空白表示を正常結果とみなしている
物件区分追加時の影響範囲区分追加は「対象区分／件数SQL／評価額SQL／免税点／課税標準／自己点検」の全層に反映件数SQL層と自己点検層への反映が漏れ、部分的な追加に留まった

3. 修正案（変更前後）

修正方針は 「件数取得ディスパッチャに償却資産(03)の分岐を追加し、評価額SQLと同様に BUKKEN_KBN='03' でCOUNTする件数SQLを生成させる」こと。併せて自己点検にも03を追加する。

3-1. 償却資産用 件数取得SQL生成関数の追加

(1) 変更前ロジック

  -- 償却資産用の件数取得SQL生成関数が存在しない（土地・家屋のみ）
  FUNCTION func_sql_cre_02_tochi(...) ...
  FUNCTION func_sql_cre_03_kaoku(...) ...

(2) 変更後ロジック

  ----------------------------------------------------------------------------
  -- 件数取得SQL生成: 償却資産
  --   資産管理番号（または資産単位）でCOUNT
  ----------------------------------------------------------------------------
  FUNCTION func_sql_cre_04_shokyaku(i_tbl IN VARCHAR2, o_sql OUT VARCHAR2)
    RETURN PLS_INTEGER IS
    v_rtn PLS_INTEGER := 0;
  BEGIN
    o_sql := 'SELECT COUNT(*) FROM ' || i_tbl
          || ' WHERE BUKKEN_KBN = ''' || C_KBN_SHOKYAKU || '''';
    RETURN v_rtn;
  EXCEPTION WHEN OTHERS THEN
    v_rtn := -1;
    p_log('E', 'func_sql_cre_04_shokyaku: ' || SQLERRM);
    RETURN v_rtn;
  END func_sql_cre_04_shokyaku;

3-2. ディスパッチャ func_get_kensu への03分岐追加

(1) 変更前ロジック

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    END IF;
    -- ※ 上記以外（償却資産=03）のとき v_sql はNULLのまま

(2) 変更後ロジック

    -- ★ 物件区分ごとに件数取得SQLを選択
    IF i_kbn = C_KBN_TOCHI THEN
      v_ret := func_sql_cre_02_tochi(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_KAOKU THEN
      v_ret := func_sql_cre_03_kaoku(v_tbl, v_sql);
    ELSIF i_kbn = C_KBN_SHOKYAKU THEN
      v_ret := func_sql_cre_04_shokyaku(v_tbl, v_sql);   -- ← 追加：償却資産の件数SQLを生成
    END IF;

3-3. 自己点検 p_self_check への03追加

(1) 変更前ロジック

    -- 家屋
    v_ret := func_sql_cre_03_kaoku('DUMMY', v_sql);

    -- ※ 償却資産の件数取得関数はチェック対象に含まれていない

(2) 変更後ロジック

    v_ret := func_sql_cre_03_kaoku('DUMMY', v_sql);
    IF v_sql IS NULL THEN o_ng_cnt := o_ng_cnt + 1; END IF;
    -- 償却資産

    IF v_sql IS NULL THEN o_ng_cnt := o_ng_cnt + 1; END IF;
改善点
  • 償却資産(03)でも件数SQLが生成され、実データの件数が正しく取得される。件数>0となれば func_calc_zeigaku・func_fmt_yen の連鎖も解け、課税標準額・税額が正しく表示される。
  • 件数取得層が評価額SQL(func_sql_hyoka)と同一の3区分対応となり、区分間の非対称が解消される。
  • p_self_check に03を加えることで、今後同種の区分未対応を発行前に検知できる（NG件数として顕在化）。

※ 償却資産テーブル FIX_SHOKYAKU_<年度> の件数カウント単位（資産管理番号単位か行単位か）および BUKKEN_KBN 格納値は、実テーブル定義書と照合のうえ確定すること。土地のような名寄せ（大字・小字・地番でのGROUP BY）が償却資産に必要かは業務仕様で要確認。文字コード（Shift-JIS）で本体管理のため、修正時のコメント文字化けにも留意。

4. 再発防止策

4-1. プログラム

No対策目的
P-1物件区分を扱う全関数（対象区分／件数SQL／評価額SQL／免税点／課税標準／自己点検）を1つの「区分対応チェックリスト」で管理し、区分追加時に全層の反映を必須化する局所的な追加漏れ（今回のような件数層のみ未対応）の防止
P-2func_get_kensu で件数SQL未生成（v_sql IS NULL）となった場合は0件返却ではなく WARN以上のログ＋ステータス異常を返し、既知区分の未対応を沈黙させない障害の早期顕在化
P-3p_self_check の点検対象を p_get_target_kbn_list が返し得る全区分と機械的に突合させ、未対応区分をNG検出するリリース前の網羅的な整合検証
P-4件数>0だが税額0（免税点未満）と、件数0（データ無し／未対応）を区別できるステータス設計にする「空白の理由」の切り分けを容易にする

4-2. テスト

  • 3帳票種別（評価110／公課120／償却130）× 3物件区分（土地01／家屋02／償却03）の組合せで、件数・課税標準額・税額の算出値を実データで検証するテストケースを追加。
  • 償却資産が存在する所有者で償却資産証明書を発行し、件数≠0かつ課税標準額・税額が空白でないことを確認する回帰テストを常設化。
  • 免税点未満（税額0が正当）のケースと、区分未対応（バグ）のケースを別テストとして分離し、空白表示の原因を取り違えない。
  • p_self_check のNG件数=0を、リリース判定のチェック項目に組み込む。

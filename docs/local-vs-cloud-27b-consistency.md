# 百炼在线 Qwen3.8-27B vs 自建服务器部署 27B — 能力一致性分析

> 技術決定記録（Technical Decision Record）
> 目的：オンライン（阿里云百炼）で行った 27B 検証結果が、お客様環境でのローカル部署 27B の能力を代表できるか、また両者の「主要能力」が一致するかを整理する。
> 最終更新：2026-08-19 ／ 維護：AI Team

---

## 0. TL;DR（結論先行）

**RCA タスクにおける「主要能力」（バグ特定・根因推論・修正提案）は、精度と設定を揃えれば、オンライン百炼と自建部署でほぼ一致する。**

理由：両者は**同一のオープンウェイト（重み）**を使う。モデルの知識・推論能力は重みに由来し、部署場所では変わらない。

ただし一致を保証するには、以下 **4 つの変数**を制御する必要がある（重要度順）：

| # | 変数 | 影響度 | 対策 |
|---|------|:---:|------|
| 1 | **量子化精度** | ★★★ | q8_0 / bf16 を使う。**4bit（q4/nvfp4）は避ける** |
| 2 | **コンテキスト長（num_ctx）** | ★★★ | 明示的に 128K+ に設定（Ollama 既定 ~4K は静かに切り捨てる） |
| 3 | **thinking / サンプリング設定** | ★★ | thinking=high を揃える。temperature 等も近づける |
| 4 | **推論エンジン実装差** | ★ | 実務上ほぼ無視可（vLLM/llama.cpp/MLX の微差） |

---

## 1. 前提の整理 — 何と何を比べるのか

### ⚠️ MLX 形式についての注意
`ollama.com/library/qwen3.8:27b-mlx-bf16` の **MLX は Apple Silicon（Mac Mシリーズ）専用**であり、**NVIDIA GPU では動作しない**。
お客様サーバー（NVIDIA GPU：RTX 5080 / 4090 級）では、実際には **GGUF（Ollama / llama.cpp）** または **vLLM / SGLang** を使う。したがって MLX は本件の比較対象外とする。

### 比較対象
| | 重み | 精度 | 推論エンジン | 提供主体 |
|---|------|------|------------|---------|
| **A. 百炼オンライン** | 公式 qwen3.8-27b | 阿里非公開（bf16/fp8 と推定） | 阿里自建（vLLM系と推定） | 阿里云 |
| **B. 自建 GGUF** ← 本命 | 同一オープンウェイト | q8_0 / bf16（推奨） | Ollama / llama.cpp | お客様 |
| C. 自建 MLX | 同一オープンウェイト | mlx-bf16 | MLX | Mac のみ（対象外） |

**要点：A と B は同じ重み。** 「知能」の源は重みなので、原理的に主要能力は一致しうる。差が出るとしたら以下の 4 変数のいずれか。

## 2. 一致性に影響する 4 つの変数

### 2-1. 量子化精度 — 影響最大・最も制御可能 ★★★

同一の重みでも、量子化のビット数で品質が変わる。RCA（コード解析）への影響：

| 精度 | 品質 | RCA への影響 |
|------|------|------------|
| **bf16 / fp8 / q8_0** | ほぼ無損失 | ✅ 百炼オンラインとほぼ一致 |
| q4_K_M / nvfp4（4bit） | 体感できる劣化あり | ⚠️ コード記号・PL/SQL の境界条件・長い推論チェーンで**細部を取りこぼす**ことがある（RCA が最も損をする箇所） |

**判断：**
- 百炼オンラインは高精度（bf16/fp8 と推定）。
- 自建は **q8_0 または bf16 必須**（`ollama/qwen3.8-27b-runbook.md` の決定と一致）。これで初めて A と揃う。
- **4bit は RCA 生産用途では非推奨。**「モデルが悪い」のではなく「量子化の選択ミス」で品質が落ちる。

### 2-2. コンテキスト長 num_ctx — 隠れた落とし穴 ★★★

- 百炼オンライン：長コンテキストを十分に確保している。
- **Ollama 自建：既定 num_ctx が約 4K しかなく、長いコードを静かに切り捨てる** → 品質が「見かけ上」低下する。

→ **自建では num_ctx=128K+ を明示設定必須**（runbook でも指摘済み）。これは能力差ではなく設定問題。

### 2-3. thinking / サンプリング設定 — 中程度 ★★

- 実測：百炼オンライン 27B は**既定で thinking が有効**（レスポンスの usage に reasoning_tokens が計上される）。これが「パイプラインなしでも非対称の欠落を検出できた」一因。
- 自建で **thinking を無効／浅くすると、同じモデルでも解析の深さが落ちる**。
- temperature / top_p 等のサンプリング差も出力のばらつきを生む。

→ 自建は **thinking=high + 近いサンプリング設定**に揃える。

### 2-4. 推論エンジン実装差 — 影響最小 ★

vLLM / llama.cpp / MLX の間には演算子実装・数値精度の微差があり、**トークン単位では完全一致しない**ことがある。しかし「バグを見つけられるか」「推論チェーンが妥当か」という**タスクレベルの能力にはほぼ影響しない**。無視してよい。

## 3. 本プロジェクトへの含意

1. **百炼オンラインの検証結果は、お客様ローカル 27B の能力上限を代表できる**
   — 前提：ローカルを **q8_0/bf16 + 128Kコンテキスト + thinking有効**で運用すること。

2. **この事実は、むしろパイプラインの価値を補強する。**
   ローカル部署には「設定の落とし穴」が多い（量子化の選択・num_ctx・thinking）。どれか一つでも外すと、同じ 27B でも品質が百炼オンラインより落ちる。
   **パイプラインのチェックリスト／工程分割／決定的検索は、こうした環境要因による品質のばらつきを吸収する** → 「品質は工程で安定させる」という設計思想（`docs/why-pipeline-for-local-llm.md`）と完全に一致。

3. **4bit 量子化を RCA 生産に使わない。**

---

## 4. 一致性の検証方法（実行可能な手順）

決定的に確認するには、お客様ローカル 27B（GGUF q8_0）が稼働後、**同一ケース＋同一パイプライン**で突合する：

```bash
# ローカル27B（例：Ollama 経由、q8_0）を pi の provider に登録した上で
bash pipeline/rca_27b.sh \
  examples/case_shinsa/QA_41001.txt \
  examples/case_shinsa/src \
  examples/case_shinsa/障害解析報告書_QA41001_local27b.html \
  <local-provider>/<qwen3.8-27b-q8_0>

# 既存のオンライン版レポートと突合（核心結論が一致するか）
#   examples/case_shinsa/障害解析報告書_QA41001_qwen38_pipeline.html  ← 百炼オンライン
```

**突合の観点：**
- 直接原因の関数特定（`func_get_kensu` の 03 分岐欠落）が一致するか
- 非対称の欠落（件数のみ未対応）を検出できているか
- チェックリスト C1–C8 の回答品質が同等か

核心結論が一致すれば、「オンライン検証＝ローカル能力の代表」が実証される。

## 5. まとめ

| 論点 | 結論 |
|------|------|
| 主要能力（バグ特定・根因・修正）は一致するか | ✅ **する**（同一重みのため）。ただし精度・設定を揃えることが条件 |
| MLX 版は使えるか | ❌ Mac 専用。NVIDIA サーバーでは GGUF/vLLM を使う |
| 4bit 量子化は | ⚠️ RCA には非推奨。q8_0/bf16 を使う |
| オンライン検証はローカルを代表できるか | ✅ できる（q8_0/bf16 + 128K + thinking 前提） |
| 未制御時のリスクは | パイプラインが吸収（品質の安定性が本方式の主眼） |

**ひと言でいえば：** モデルの「地力」は重みで決まり部署場所に依らない。差が出るのは**量子化・コンテキスト・thinking という運用設定**であり、これらを揃え、かつパイプラインで工程を固めれば、ローカル自建でもオンラインと同等の主要能力を安定して引き出せる。
